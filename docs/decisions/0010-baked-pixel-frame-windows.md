# Decision 0010 — One window system: baked pixel frames from the Pixel Frame engine

**Status:** Proposed by Claude and accepted by Ariel on November 9, 2026. **W2.1–W2.3 implemented November 9** (core port, interior fill, bake tool; the UI theme file and battle windows; then every page window; see the notes below and [STATUS](../STATUS.md)); W2.4 is not started. It changes how [0009](0009-classic-battle-interface.md) draws its battle windows and will replace the W1 windowskin ([WINDOW-SKIN.md](../WINDOW-SKIN.md)) once the replacement matches it.

## Context

- **W1 windowskin.** Page windows (dialogue, Settings/Debug drawer, dividers) use Ariel's edited `Window.png` atlas: 64 roles in an 8 × 8 grid of 16 px tiles, composed by `skin/layout.ts` and `skin/paint.ts` into an element background. It supports live title gaps and fixed edge midpoints. Colour lives in the art; the semantic tokens in `tokens.css` colour everything else. [UI-DESIGN-SYSTEM](../UI-DESIGN-SYSTEM.md) expects future themes to remap tokens and supply compatible art.
- **M5.3c battle windows.** These were built with a separate Phaser `Graphics` renderer and hard-coded `PANEL_STYLE` colours. That bypasses the skin, the tokens and the theme path, so changing the game's look would not reach battles. This was a mistake, now recorded here.
- **Pixel Frame demonstrator.** Ariel's own pixelstudio project (`J:\pixelstudio\dist\pixel-frame-demonstrator.zip`, reviewed November 9; its 28/28 engine tests pass).
  - **How it builds frames:** from data. A height profile is swept around the box, corner art is mirrored into four corners, and edge motifs and medallions are optional.
  - **Lighting:** normal maps, palette-quantised lighting, outline and drop shadow.
  - **Styles and states:** 16 styles in control, panel, showpiece and neutral tiers; states for hover, pressed, focus, active and disabled.
  - **Themes:** named themes plus a one-colour **Custom** theme generated with hue-shifted ramps.
  - **Accessibility:** a high-contrast mode and a forced-colours fallback.
  - **Scaling:** whole-device-pixel scaling at fractional DPR.
  - **Bake:** renders each style and state once into small 9-slice PNGs; the baked frames rebuild the live frame pixel-for-pixel at other sizes (its test 17).

## Decision

### 1. One frame source for every window, baked at build time

- All game windows come from **baked 9-slice frame images** generated by a port of the Pixel Frame core. That covers dialogue, menus, Settings, inventory, saves and the battle windows.
- **Page windows** use them as CSS `border-image`. **Canvas windows** (battle) use the same PNGs as Phaser `NineSlice` textures (available in Phaser 4.2.1).
- Theme, style, palette and size of each window come from content, so one change re-skins page and canvas windows together.
- **Bake, never light at runtime.** Frames are generated by a Node tool next to `tools/generate-assets.mjs`. It uses the existing zlib PNG writer, so no new dependency. The output is hashed images plus a small frame manifest in the generated assets: deterministic, reproducible and cosmetic only. The live lighting engine, the cursor lamp, `attach.js` and its animation loop stay in pixelstudio.

### 2. What is ported, and how

- **Ported to strict TypeScript, DOM-free:** the core (profile, art stamps and corners, frame composition, normals, shading, palettes and themes, bake geometry), about 1,500 lines today.
  - It moves off the `window.PF` global and the browser-only `ImageData`, `location`, `matchMedia` and `localStorage` calls.
  - It outputs plain RGBA arrays.
  - It sits in its own module folder with unit tests carried over from the demonstrator's checks: profile sweep, mirrored-corner normals, 9-slice exactness, palette-only output, one-colour themes, high contrast and PNG corner round trips.
- **Not ported:** demo pages, workbench, inspector, settings panel, live attach and animation. Corner art authored in the pixelstudio workbench comes across as PNG files using its documented colour conventions.
- **Provenance and licence (decided by Ariel, November 9):** pixelstudio is Ariel's own work. The ported code joins RPGameworks under **the same licence as RPGameworks**. The project has not selected a licence yet (README), so until it does, the ported code carries no licence grant, like the rest of the repository. When the project licence is chosen, it covers this code with no separate decision. The first W2.1 commit records the origin (pixelstudio, Pixel Frame demonstrator, Ariel) in the module's header and in the asset provenance notes.

### 3. Additions the engine needs for our windows

- **Interior fill.** The engine frames the border only. Windows need a baked interior: flat, vertical gradient, or stepped bands (the 16-bit look), with themed colours. The fill is part of the 9-slice centre so it stretches exactly.
- **A Final Fantasy-style preset.** Thin `flat` or `round` profile, subtle or no flair, no brushed metal or wear, white-to-pale-blue border ramp, deep blue banded fill. This replaces `PANEL_STYLE` and is Ariel's chosen battle look. Base colour and preset are content, tuned in play review.
- **Titles and midpoints.** A plain 9-slice cannot cut a live title gap or keep a fixed edge midpoint. W1 has both. Titles become a separate baked **nameplate** (the engine's `plate` style) laid over the top edge, with live text on it. Midpoint ornaments return only if a later 11-slice or overlay piece is added. Until the dialogue reaches parity on these, the W1 dialogue keeps its atlas.
- **States for focusable windows and buttons** use the engine's baked states. The battle menu keeps its own ▶ cursor and does not need button frames.

### 4. Theme data

- A versioned, schema-validated UI theme file in the game content. It holds a theme (named or one base colour), a contrast mode, the window style per surface (dialogue, menu, battle, list), the fill and the pixel scale rules.
- The token colours in `tokens.css` that describe window surfaces derive from the same theme, so text and focus colours stay matched to the frames.
- Changing the theme is a content edit plus a rebuild; no code changes.

### 5. Replacing W1

- W1's atlas, manifest, audit tool and compositor stay working until the baked frames reach parity on the dialogue, Settings drawer and divider: comparison captures, forced colours, narrow layout and the existing browser checks.
- They are then retired in one packet. `Window.png` stays in history as Ariel's accepted art. If its silver-and-midnight look should survive, it is reproduced as a theme preset rather than kept as a second system.

### 6. Canvas text in battle

- [UI-DESIGN-SYSTEM](../UI-DESIGN-SYSTEM.md) excluded "canvas-only text UI". The battle draws its window text on the canvas (UNSCII baked to a bitmap) for exact pixels.
- This is accepted as a battle-only exception, on the condition [0009](0009-classic-battle-interface.md) already enforces: a complete DOM layer with real focusable buttons and screen-reader text. Page windows stay real HTML text. UI-DESIGN-SYSTEM is updated to say so when this lands.

## Correction during W2.1 (November 9, 2026)

§3 said the fill would be part of the 9-slice centre "so it stretches exactly". That only holds for a flat fill: banded and gradient fills depend on the window's height, and a stretched centre would scale the bands by fractions of a pixel. Frames are therefore baked with a transparent centre, and the fill is a separate pure function, `fillColumn(fill, height)`, drawn as a one-pixel-wide column stretched sideways, which is exact at any width. The manifest records each frame's fill. Canvas windows draw the column as a texture; page windows can use a flat background or hard-stop gradient built from the same column.

## Note from W2.2 (November 9, 2026)

The theme file is the bake's input, not a runtime file: `tools/bake-frames.ts` reads `content/games/demo/ui-theme.json` and writes everything the game needs, including the battle text colours, into `generated/frames/manifest.json`. Battles that cannot load the manifest draw plain fallback windows (the only remaining hard-coded window colours) and report `frames: 'fallback'` in the runtime snapshot.

## Notes from W2.3 (November 9, 2026)

- **One look everywhere.** Ariel chose the classic blue for page windows too, so the silver-and-midnight W1 look is not kept as a preset for now.
- **Nameplate placement.** Titles sit on a baked nameplate inside the top of the window rather than across the top edge, which stays correct at every padding and scale; long titles wrap inside the plate. Midpoint ornaments are not reproduced.
- **Page fill.** CSS cannot know an element's height, so `window-frames.ts` repaints each window's banded fill as a hard-stop gradient from `fillColumn` when its size changes (one scheduled invalidation, as W1 did).
- **Minifier.** The production CSS minifier drops the value of `border-image: none`; the forced-colours rules use `border-image-source: none`.
- **Not yet:** the inner control tokens still come from `tokens.css` rather than the theme, and the UI gallery fixture still mounts W1 until W2.4.
