## UNSCII 16 interface font and pixel-sharp battle text — November 9, 2026, local

Ariel's play review found the battle stage labels blurry: they were 10–14 px system-font canvas text with a stroke, smoothed by the browser and then upscaled. The stage now draws its text in **UNSCII 16** (`public/fonts/unscii/unscii-16.ttf`, byte-identical to the copy in Dungeonminusdelver; provenance and terms in `public/fonts/CREDITS.md`: plain UNSCII is public domain and Ariel confirmed it free for games on 2026-10-23). Measured in Chromium, the TTF's outlines come out anti-aliased at every size and position, so `src/presentation/pixel-font.ts` rasterises each printable ASCII glyph once at 8× and samples each pixel cell's centre, which recovers the exact 8 × 16 one-bit design with no ambiguous samples, then registers it as a Phaser RetroFont drawn with BitmapText at 1:1, nearest filtering, fill tint and a hard one-pixel shadow. A 1920 × 1080 capture of an HP label contains exactly three colours (background, shadow, text). The battle view registers the font texture when it opens and removes it on destroy, so texture counts still return to their pre-battle values; if the font fails to load, labels fall back to plain monospace canvas text and the battle still starts. At 8 px per character, names no longer fit beside neighbouring battlers, so the stage labels show HP only (`20/20`); names stay in the command window.

**Whole interface:** at Ariel's request every DOM surface (dialogue, buttons, menus, inventory, saves, settings and tools) now uses UNSCII 16 through the shared tokens in `tokens.css` (an `@font-face` for the same file; Vite rewrites its URL for the Pages base path). Every text-size token is the 16 px design size, single-glyph icons (d-pad arrows, close) use 32 px, letter spacing is zero, and `font-synthesis: none` keeps bold rules at the font's single weight. **Known limit:** the TTF's outlines sit exactly on the pixel grid at 16 px (64 units per em, every coordinate a multiple of 4), but Chromium on Windows still gives DOM text a one-pixel horizontal grey edge from DirectWrite. `-webkit-font-smoothing`/`font-smooth` do nothing on Windows, and patched `gasp` flags (no greyscale) produced identical output, so only canvas text is guaranteed exactly sharp.

## M5.3a timeline battle kernel — November 8, 2026, local

M5.3 was split in two. **M5.3a** (this packet) replaces the round-based practice kernel with the turn-timeline rules from [decision 0006](decisions/0006-battle-system-direction.md); **M5.3b** will replace the interim dialogue-window presentation with a dedicated side-view battle scene.

**Rules (`src/domain/battle.ts`, pure TypeScript):** every combatant has a next-action tick. The living combatant with the lowest tick acts; ties go to the party, then the lower slot. Acting adds `ceil(1000 × weight / (100 × speed))` ticks, with weights Attack 100, Item 80 and Guard 60, so lighter actions come around sooner. The kernel exposes an 8-turn timeline and `preview(command)`, computed from the same rule without randomness, so the order shown is the order executed until the hero's next decision, apart from combatants who are defeated first. Damage keeps the seeded `max(1, attack − defense ± 1)` stream. Guard halves every hit, rounding up, until the hero acts again. An item heals one living ally, up to full; healing at full HP is refused. Escape always ends an ordinary battle. Enemy turns resolve automatically until the next hero decision; a faster enemy can act before the hero's first turn. `validate` returns a reason (wrong phase, invalid or defeated target, unusable item, full HP, unknown command) without touching state or randomness. Retry is available only after defeat and restores the identical opening; spent items are not refunded.

**Content:** the encounter catalog is now version 2 with `party` (1–4) and `enemies` (1–6), each combatant having an ID, name, battler atlas frame, HP, attack, defense and **speed**. Validation rejects duplicate combatant IDs, blank names and unknown battler frames. Items may declare `battleUse: {type: "heal", amount}`. The demo Practice Sigil encounter is now the hero (30 HP, speed 10) against the Practice Sigil (20 HP, speed 8) and a faster Sigil Shard (10 HP, speed 14). A new Workshop tonic (heals 12, stacks to 9) comes from a new supply crate in the Supply Room that grants two. The new item and placement IDs are additive; per the early-demo policy no migration was needed.

**Interim presentation:** the dialogue window now shows both sides' HP, the resolved events, whose turn it is, and the next six turns ("Next: Hero → Practice Sigil → …"). Commands are one button per living enemy (Attack …), Guard, a tonic button with the carried count (disabled with "HP is already full." when it cannot help) and Escape. After each command the results are shown with Continue. Using a tonic first commits a session transaction that removes one; the battle resolves only if it committed. Cancel continues past results, otherwise escapes. Impact effects still play after resolution. The runtime snapshot's `battle` now reports turn, active combatant, HP by ID and the timeline.

**Verification:** `npm run validate` accepted 4 maps, 672 cells and 6 exits (131 definitions, 189 references, the same four advisories). `npm run check` passed strict typecheck, **406/406** unit/content tests and the build. The kernel's 12 tests cover delays, tie order, a faster enemy's opening hit, a pinned seeded trace through victory, more than 200 randomized decisions checking that execution matches the preview, lighter Guard previews, invalid commands not consuming randomness, Guard halving, healing, Escape, defeat and Retry, and v2 catalog and item validation. The first full run had one stale unit test (it built a version-1 catalog and pointed at the sigil's old object index); it passed after the update. `npm run test:browser` passed **154/154**, including five battle scenarios: the full timeline battle to victory with restored focus and an unchanged session; collecting two tonics, using one (inventory drops to 1) and escaping without a refund; failed catalog load; narrow-screen controller cancel and pointer Escape with bounded resources; and authored defeat with an identical Retry opening. Writing the tonic test exposed two test-side mistakes (a pure turn needs a held key; enemies act after the tonic), both corrected before the passing run. Ariel has not yet played this candidate.

## CA1 character pack v1 foundations — delivered (synthetic pixels only)

The character pack format, deterministic offline encoder, and strict runtime reader exist and are tested end to end against synthetic pixels; no licensed pixels, `.import/` input, or runtime fetch is involved. Recorded as [decision 0003](decisions/0003-character-pack-v1.md), which owns the full wire layout: magic `RPGP`, version byte 1, reserved 0, bounded UTF-8 JSON manifest, then zlib-compressed raw RGBA payloads addressed by deduplicated manifest entries (`payloads` with sequential offsets/lengths/decodedLengths/SHA-256 digests; `cells` binding animation|direction|frameIndex × layer → payload). Every payload decodes to exactly the uniform cell size; fail-closed bounds: manifest ≤ 256 KiB, decoded payload ≤ 128×128 RGBA, total decoded and payload body ≤ 8 MiB, ≤ 65 535 payloads / 65 536 cells / 16 layers / 256 animations / 16 frames per animation, plus ≥1 layer per animation frame with subset layer coverage permitted per frame.

The encoder (`tools/build-character-pack.mjs`, explicit command, never part of routine `npm run build`) validates a JSON pack source through `schemas/character-pack-source.schema.json` plus cross-field rules (duplicate animation/layer IDs, unknown layers, frameIndex beyond declared frameCount, wrong pixel-symbol counts, unknown palette symbols, missing frames), then encodes byte-identically across runs and invariant to source frame order (deflate level 9, canonical walk, no timestamps), writing `<packId>.rpgpack` and a `<packId>.report.json` generation report (source/pack hashes, byte and cell/payload counts) only after full validation, via staging plus rename. Pair replacement is ordered recoverably: the regenerable report (`regenerable: true`, never authoritative — the pack blob is the artifact of record) is replaced first and the pack second; a failing pack replacement surfaces a contextual error and preserves an existing pack while the report remains regenerable; rerunning the command re-derives the pair from scratch. The report records a repository-relative source identifier for in-repo inputs. The runtime reader (`src/platform/character-pack.ts`) verifies framing, strict UTF-8 JSON (schema `schemas/character-pack-manifest.schema.json`, ajv-standalone generated alongside the content validators), cross-field manifest structure (sequential payload offsets, exact payload-body extent, uniform decoded sizes, cell uniqueness, animation coverage, direction consistency, payload index/layer references), and decodes payloads lazily through `DecompressionStream` with a chunk-wise decoded-length cap — a hostile pack declaring a 64-byte payload over a 1 MiB deflate stream is cut off mid-read — and per-payload SHA-256 verification after inflation; corrupt compressed streams surface a clear failure instead of an opaque DOM error. Cancellation is reader-owned: an abort signal interrupts an in-flight read by cancelling the held reader (the `pipeThrough`-locked source is never touched, which previously rejected while discarded), tested for in-flight aborts, abort during digest verification, already-aborted signals, and completed decodes. The reader is data-only: no eval, no paths, no network. `tools/generate-schemas.mjs` now also generates the manifest validator/declarations.

Three fixed manual slots use a version-1 envelope and IndexedDB database `rpgameworks` / store `saveSlots`. Loading validates IDs and the checkpoint, constructs a candidate session and room invisibly, and swaps them only after preparation succeeds. If IndexedDB is unavailable, gameplay stays session-only while current-session export and validated import-to-current-session remain usable.

Malformed/current-versus-previous data, wrong games, future/incompatible versions, unknown IDs, invalid values/checkpoints, controlled unavailable/quota/abort failures, stale tabs, and destination preparation failures are distinct rejection paths.
